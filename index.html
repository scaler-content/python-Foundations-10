What this post-read covers

Why classes exist; classes vs. objects; __init__ and self; instance attributes and methods; class variables vs. instance variables (and the shared-mutable-list bug); encapsulation; abstraction; inheritance and super(); method overriding; polymorphism; and a cumulative mini project.

01 · the idea

What if we need to track 50 dogs, not one?

Suppose we're building a program to track dogs at a shelter — each dog has a name, a breed, and an age. We could store one dog like this:

dog_name = "Rex"
dog_breed = "Labrador"
dog_age = 3
🔮 Before you reveal: now imagine tracking 50 dogs. What starts to go wrong with this approach?

A separate set of variables per dog, no clean way to loop over "all dogs," and no obvious way to attach behavior — like making a dog bark — to one specific dog. What we really want is a single "thing" that bundles a dog's data and its behavior together, and lets us create as many of these things as we need. That's exactly what a class gives us.

✅ TakeawayA class lets you bundle related data and behavior into one reusable definition, instead of juggling separate variables per thing you're tracking.
02 · classes & objects

The blueprint idea

A class is a blueprint — it describes what a dog looks like in general, without being any particular dog. An object is one actual dog, built from that blueprint. We call each object an instance of the class.

Mental modelA blueprint for a house doesn't limit you to building only one house. You can make as many instances as you want from the same class.
✅ TakeawayClass = the blueprint/definition. Object (instance) = one thing built from that blueprint. Every object from the same class shares the same structure, but holds its own data.

04 · creating objects

Are two dogs from the same class the same thing?

🔮 Predict before revealing: are rex and fido the same object, or two separate ones?
class Dog:
    pass

rex = Dog()
fido = Dog()

print(rex)
print(fido)
print(rex == fido)

<__main__.Dog object at 0x7f3a1c0a4d90>
<__main__.Dog object at 0x7f3a1c0a4e10>
False

(Addresses will vary.) Each call to Dog() builds a brand-new, independent object. Two dogs made from the same class are still two separate things — exactly like two houses built from the same blueprint.

✅ TakeawayCalling Dog() creates a new, independent object every time — even if it comes from the exact same class.
05 · the __init__ constructor

Giving every object a starting state

Right now our Dog objects don't hold any data — they're empty. We want every dog to start with a name and a breed the moment it's created. That's what __init__ is for — it runs automatically every time you create a new object.

class Dog:
    def __init__(self, name, breed):
        self.name = name
        self.breed = breed
🔮 Predict both lines before running
rex = Dog("Rex", "Labrador")

print(rex.name)
print(rex.breed)

Rex
Labrador
📌 Note__init__ is called automatically — you never write rex.__init__(...) yourself. Writing Dog("Rex", "Labrador") is what triggers it, with self filled in by Python.
06 · understanding self

The most confusing word in this class

self simply means: "the specific object this method is being run on." When you write rex.bark(), Python quietly passes rex in as self — you never type it yourself when calling a method, only when defining one.

🔮 Both objects were built from the same __init__ code — will rex.name and fido.name be the same value or different?
class Dog:
    def __init__(self, name):
        self.name = name

rex = Dog("Rex")
fido = Dog("Fido")

print(rex.name)
print(fido.name)

Rex
Fido

Same __init__ code ran twice, but self.name = name pointed at a different self each time — that's the whole trick behind self.

✅ Takeawayself isn't a Python keyword — it's the near-universal convention for naming the first parameter of a method, and it refers to whichever object called that method.
07 · instance attributes

Data that belongs to one specific object

Values stored using self. inside __init__ (or any method) are called instance attributes — they belong to one specific object.

rex = Dog("Rex")

rex.age = 3   # can also add an attribute directly, after creation
print(rex.age)
📌 NoteSetting attributes directly like this works, but it's fragile — if you forget to set rex.age before reading it, you'll get an AttributeError. Setting every attribute inside __init__ guarantees every object starts complete.
08 · methods

Functions that live inside a class

A method is just a function defined inside a class — and like __init__, it always takes self as its first parameter.

class Dog:
    def __init__(self, name):
        self.name = name

    def bark(self):
        print(f"{self.name} says Woof!")
🔮 Predict the output before running
rex = Dog("Rex")

rex.bark()

Rex says Woof!

bark(self) reads self.name to get "Rex" specifically — the method's behavior depends on which object called it, which is the entire point of putting it inside the class.

09 · attributes + methods together

Methods can change an object's own state

class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def describe(self):
        return f"{self.name} is {self.age} years old."

    def have_birthday(self):
        self.age += 1
🔮 Predict both describe() outputs — has age changed between them?
rex = Dog("Rex", 3)

print(rex.describe())

rex.have_birthday()

print(rex.describe())

Rex is 3 years old.
Rex is 4 years old.

have_birthday() modifies self.age directly — methods can change an object's own attributes, which is how objects keep track of state over time.

10 · class vs. instance variables

Data shared by every object vs. data unique to one

Everything stored so far — name, age — belongs to one specific dog. Those are instance variables. Sometimes, though, a piece of data is true for every object of a class, not just one. For that, we use a class variable — written directly in the class body, not inside __init__.

🔮 Both dogs share the same class — will species match for both?
class Dog:
    species = "Canis familiaris"   # class variable — same for every dog

    def __init__(self, name):
        self.name = name   # instance variable — unique per dog

rex = Dog("Rex")
fido = Dog("Fido")

print(rex.species)
print(fido.species)

Canis familiaris
Canis familiaris

This feels perfectly safe, and it is — species is a string, and strings are immutable. Reassigning rex.species = "..." would just create a new instance variable that shadows the class one for rex specifically, leaving fido untouched. The danger shows up with a different kind of value.

11 · when class variables go wrong — the vote

The most counterintuitive idea in this class

After rex learns a trick, will fido's tricks list also show "sit," or will it stay empty?

class Dog:
    tricks = []   # class variable — a list, this time

    def __init__(self, name):
        self.name = name

rex = Dog("Rex")
fido = Dog("Fido")

rex.tricks.append("sit")

print(rex.tricks)
print(fido.tricks)

💬 The output is:

['sit']
['sit']

fido never learned anything — we only called rex.tricks.append("sit"). But there's only ever one tricks list. It belongs to the Dog class itself, not to rex or fido individually — every dog is just looking at the exact same list. When rex.tricks.append("sit") ran, it modified that one shared list in place — the same way .append() mutates a list directly. fido isn't broken. fido.tricks was never its own list to begin with.

🤖 AI momentIf you guessed fido's list would stay empty, paste this into a general-purpose AI assistant: "I expected fido.tricks to stay empty since I only modified rex.tricks, but it changed too. Walk me through exactly why, step by step." Then independently verify: rewrite the class so each dog gets its own list (see the next card) and confirm rex.tricks.append("sit") no longer affects fido.tricks.
✅ TakeawayEvery instance of a class shares one copy of a mutable class variable unless each object is given its own inside __init__. This is one of the most common real bugs in beginner (and professional) Python OOP code.
12 · fixing it

Mutable defaults belong in __init__

The fix is to give each object its own list, created fresh inside __init__:

🔮 Has moving the list into __init__ changed the outcome?
class Dog:
    def __init__(self, name):
        self.name = name
        self.tricks = []   # instance variable now — a brand-new list per dog

rex = Dog("Rex")
fido = Dog("Fido")

rex.tricks.append("sit")

print(rex.tricks)
print(fido.tricks)

['sit']
[]
✅ TakeawayUse a class variable for data that's genuinely the same for every object (like a constant). Use self.x = ... inside __init__ for anything that should belong to one object individually — especially anything mutable, like a list or dictionary.
13 · encapsulation

Bundling data with the methods that control access to it

Encapsulation means bundling data and the methods that work on it together, and controlling how that data is accessed from outside the class. In Python, a leading double underscore signals "this is internal, please don't touch it directly."

class BankAccount:
    def __init__(self, balance):
        self.__balance = balance   # double underscore

    def get_balance(self):
        return self.__balance

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount
🔮 Predict the output
account = BankAccount(100)

account.deposit(50)

print(account.get_balance())

150
🔮 We used get_balance() instead of reading __balance directly. Does the double underscore actually block direct access, or does something else happen?
print(account.__balance)

AttributeError: 'BankAccount' object has no attribute '__balance'

Python doesn't have true private attributes the way some other languages do. A double-underscore name actually gets internally renamed to _BankAccount__balance — a process called name mangling — which is why the direct name lookup fails. It's still technically reachable as account._BankAccount__balance, but that's exactly the point: encapsulation in Python is a strong convention and a speed bump, not an unbreakable lock.

✅ TakeawayEncapsulation restricts direct access to data — the deposit() method exists so nobody needs to reach around it in the first place.
14 · abstraction

Hiding complexity behind a simple name

Abstraction means hiding complicated internal steps behind a simple method name — the caller just needs to know what to call, not how it works inside.

account.deposit(50)

Whoever calls account.deposit(50) doesn't need to know that it checks amount > 0, or how __balance is stored internally. They just need to know: call deposit(), give it an amount, done. That's abstraction — a simple interface hiding the messy details behind it.

📌 NoteEncapsulation and abstraction work together but aren't identical: encapsulation restricts direct access to data; abstraction presents a simple interface regardless of how complex the internals are.
15 · inheritance

Reusing another class's code

Suppose we want a Manager class and a Developer class — both are employees, and both share things like a name and a salary. Writing that shared code twice would be wasteful. Inheritance lets a class reuse another class's attributes and methods.

class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def describe(self):
        return f"{self.name} is an employee."

class Manager(Employee):
    pass
🔮 Manager has no __init__ or describe() of its own — do these lines work at all, and if so, what do they print?
mgr = Manager("Asha", 90000)

print(mgr.name)
print(mgr.describe())

Asha
Asha is an employee.
✅ TakeawayManager(Employee) means "Manager inherits from Employee." Everything Employee can do, Manager can do too, automatically — without writing a single line of new code.
16 · the super() function

Letting the parent class finish its own setup

Manager didn't need its own __init__ because it doesn't add anything new yet. But what if Manager needs an extra piece of data Employee doesn't have — like team_size?

class Manager(Employee):
    def __init__(self, name, salary, team_size):
        super().__init__(name, salary)   # let Employee set up name and salary
        self.team_size = team_size
🔮 Predict both lines before running
mgr = Manager("Asha", 90000, 5)

print(mgr.name)
print(mgr.team_size)

Asha
5
✅ Takeawaysuper().__init__(name, salary) calls Employee's own __init__ on this same object, so name and salary get set up exactly the way Employee already knows how to do it. Manager's __init__ then only has to handle what's actually new. Forgetting this line is a very common mistake.
17 · method overriding

Replacing a method entirely

A subclass can also replace a method entirely, instead of just adding new attributes.

class Manager(Employee):
    def __init__(self, name, salary, team_size):
        super().__init__(name, salary)
        self.team_size = team_size

    def describe(self):
        return f"{self.name} manages a team of {self.team_size}."
🔮 Employee also has a describe() method — which version runs: Employee's, or Manager's?
mgr = Manager("Asha", 90000, 5)

print(mgr.describe())

Asha manages a team of 5.
✅ TakeawayThis is called overriding — Manager's own describe() takes priority over Employee's version, for any Manager object specifically. Python always checks the object's own class first before looking at the parent.
18 · polymorphism

Same method name, different behavior

Polymorphism means "many forms" — the same method name behaving differently depending on which object it's called on. We've actually already built this:

class Developer(Employee):
    def __init__(self, name, salary, language):
        super().__init__(name, salary)
        self.language = language

    def describe(self):
        return f"{self.name} writes code in {self.language}."
🔮 The loop calls .describe() the exact same way for every item — predict both lines of output
employees = [Manager("Asha", 90000, 5), Developer("Rahul", 75000, "Python")]

for emp in employees:
    print(emp.describe())

Asha manages a team of 5.
Rahul writes code in Python.
🤖 AI momentBefore asking AI anything, write one sentence yourself: why use inheritance here instead of three completely separate, unrelated classes? Then ask a general-purpose AI assistant the same question and compare. As a check, try removing the inheritance relationship entirely (independent classes, each with their own name/salary/describe()) — the loop above still works the same way, since Python's polymorphism only cares that emp.describe() exists, not that the objects share a parent class.
✅ TakeawayThe loop never checks "is this a Manager or a Developer?" — it just calls emp.describe() and trusts each object to know how to describe itself correctly.
19 · mini project

Employee Management System

Now combine every idea from this class into one small, realistic program: an Employee base class with a name, a private salary, and a describe() method; a Manager subclass adding team_size; a Developer subclass adding language; and a list holding a mix of employees, described uniformly through one loop.

class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.__salary = salary

    def get_salary(self):
        return self.__salary

    def describe(self):
        return f"{self.name} is an employee."


class Manager(Employee):
    def __init__(self, name, salary, team_size):
        super().__init__(name, salary)
        self.team_size = team_size

    def describe(self):
        return f"{self.name} manages a team of {self.team_size}."


class Developer(Employee):
    def __init__(self, name, salary, language):
        super().__init__(name, salary)
        self.language = language

    def describe(self):
        return f"{self.name} writes code in {self.language}."
🔮 Predict all six lines of output — three describe() lines and three salary lines, in order
employees = [
    Manager("Asha", 90000, 5),
    Developer("Rahul", 75000, "Python"),
    Employee("Priya", 60000),
]

for emp in employees:
    print(emp.describe())
    print("Salary:", emp.get_salary())

Asha manages a team of 5.
Salary: 90000
Rahul writes code in Python.
Salary: 75000
Priya is an employee.
Salary: 60000
✅ TakeawayThis program uses every core idea from this class: classes and objects, __init__ and self, inheritance with super(), method overriding, polymorphism in the loop, and encapsulation through get_salary() instead of touching __salary directly.
20 · final recap

The one idea to leave with

CLASS (blueprint) │ ┌───────┴───────┐ ↓ ↓ __init__ methods (starting (behavior, state, via via self) self) │ │ └───────┬───────┘ ↓ OBJECT (one instance, own data)

A class is a blueprint; an object is one specific thing built from it. __init__ runs automatically when an object is created, and self refers to the specific object a method is running on. Class variables are shared by every object — fine for constants, dangerous for anything mutable, since every object ends up looking at the exact same one. Inheritance lets a class reuse another class's code, super() lets a subclass still run the parent's setup, and overriding lets a subclass replace a method entirely. Polymorphism means the same method call can behave differently depending on the object. And encapsulation and abstraction both hide complexity — encapsulation restricts direct access to data, abstraction presents a simple interface regardless of internal complexity.

✅ TakeawayOOP is about bundling data and behavior together, and controlling how that bundle is built, shared, extended, and used.
